
# Epost Integration Service 项目规则文档

## 1. 概述

本文档定义了 `epost-integration-service` 项目的开发规范、代码标准、架构约束和安全要求，旨在确保团队协作高效、代码质量可控、系统安全可靠。

---

## 2. 技术栈规范

### 2.1 语言版本

| 技术 | 版本 | 说明 |
| :--- | :--- | :--- |
| Java | 17 | LTS 版本，使用模块化特性 |
| Spring Boot | 3.2.12 | 稳定版本，兼容JDK 17 |
| Spring Cloud | 2023.0.5 | 与Spring Boot 3.2.x 兼容 |
| Spring Cloud Alibaba | 2023.0.1.2 | Nacos集成支持 |
| MyBatis Plus | 3.5.x | ORM框架 |
| MySQL | 8.0+ | 数据库 |
| Redis | 7.0+ | 缓存 |

### 2.2 依赖管理

- 使用 Maven 进行依赖管理
- 依赖版本统一在父POM中定义
- 禁止引入未批准的第三方依赖
- 定期更新依赖版本，修复安全漏洞

## 3. 代码规范

### 3.1 Java代码规范

#### 3.1.1 基本约定

- **编码格式**: UTF-8
- **换行符**: Unix风格 (LF)
- **缩进**: 4个空格，禁止使用Tab
- **行宽**: 每行不超过120字符

#### 3.1.2 命名规范

| 类型 | 规范 | 示例 |
| :--- | :--- | :--- |
| 类名 | PascalCase，名词或名词短语 | `ExpressController` |
| 方法名 | camelCase，动词或动词短语 | `createOrder()` |
| 变量名 | camelCase，见名知意 | `carrierCode` |
| 常量名 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 包名 | 全小写，域名反转 | `org.example.express` |
| 接口名 | PascalCase，以 `I` 开头或使用 `-able` 后缀 | `ExpressStrategy`, `IExpressService` |

#### 3.1.3 类结构顺序

1. `package` 声明
2. `import` 声明（按字母顺序排序）
3. 类注释（Javadoc）
4. 静态常量
5. 实例变量（按访问级别排序）
6. 构造方法
7. 公共方法
8. 私有方法
9. 方法中不能有使用包名导入语句（如 `java.util.Base64`,必须在类顶部导入）
#### 3.1.4 异常处理

- 使用统一的业务异常体系
- 禁止捕获 `Exception` 后不处理
- 异常信息需包含上下文信息
- 使用日志记录异常详情

#### 3.1.5 日志规范

- 使用 SLF4J 框架（`@Slf4j`）
- 日志级别使用：
  - `DEBUG`: 调试信息，生产环境关闭
  - `INFO`: 业务关键流程记录
  - `WARN`: 警告信息，需要关注但不影响业务
  - `ERROR`: 错误信息，影响业务正常运行
- 禁止打印敏感信息（密码、Token等）

## 4. 架构规范

### 4.1 分层架构

```
┌─────────────────────────────────────────────┐
│           Controller (控制层)              │
│   - REST API入口                           │
│   - 参数校验                               │
│   - 响应封装                               │
├─────────────────────────────────────────────┤
│             Service (服务层)               │
│   - 业务逻辑处理                           │
│   - 事务管理                               │
│   - 策略调度                               │
├─────────────────────────────────────────────┤
│             Strategy (策略层)              │
│   - 策略模式实现                           │
│   - 快递服务商差异化处理                   │
├─────────────────────────────────────────────┤
│             Mapper (数据访问层)            │
│   - MyBatis Plus接口                       │
│   - 数据库操作                             │
├─────────────────────────────────────────────┤
│             Domain (实体层)                │
│   - 数据库实体映射                         │
│   - DTO定义                               │
└─────────────────────────────────────────────┘
```

### 4.2 设计模式约束

- **策略模式**: 用于快递服务商的差异化处理
- **工厂模式**: 用于策略的动态获取
- **模板方法模式**: 用于公共流程封装

### 4.3 包结构规范

```
org.example.express
├── configs/          # 配置类（@Configuration）
├── controller/       # REST控制器（@RestController）
├── domain/           # 实体类（@Entity/DTO）
├── dto/              # 数据传输对象（新增）
├── factory/          # 工厂类
├── mapper/           # MyBatis Mapper接口
├── service/          # 服务接口
│   └── impl/         # 服务实现类
├── strategy/         # 策略接口与实现
└── exception/        # 异常类（建议新增）
```

### 4.4 类职责约束

| 层 | 职责 | 禁止操作 |
| :--- | :--- | :--- |
| Controller | 接收请求、返回响应 | 直接操作数据库、业务逻辑 |
| Service | 业务逻辑处理 | 直接处理HTTP请求 |
| Strategy | 差异化业务实现 | 数据持久化 |
| Mapper | 数据访问 | 业务逻辑处理 |

## 5. 数据库规范

### 5.1 命名规范

- **表名**: 小写，下划线分隔，前缀 `t_`
  - 示例: `t_ems_order`
- **字段名**: 小写，下划线分隔
  - 示例: `order_no`, `create_time`
- **索引名**: 前缀 `idx_` + 表名 + 字段名
  - 示例: `idx_ems_order_order_no`

### 5.2 字段约束

- 主键使用 `BIGINT` 类型，自增
- 创建时间字段: `create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
- 更新时间字段: `update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
- 逻辑删除字段: `del_flag TINYINT NOT NULL DEFAULT 0`

### 5.3 MyBatis Plus规范

- 使用 `@Mapper` 注解标识Mapper接口
- 使用 `@TableName` 映射表名
- 使用 `@TableField` 映射字段名
- 实体类继承 `BaseEntity`
- 使用Lambda表达式构建查询条件

## 6. 配置规范

### 6.1 配置管理

- 使用 Nacos 配置中心管理配置
- 配置文件按环境分离（dev/test/prod）
- 敏感配置使用环境变量或密钥管理服务
- 配置项使用 `${}` 占位符引用环境变量

### 6.2 配置优先级

1. 命令行参数
2. 环境变量
3. Nacos配置中心
4. 本地配置文件（application.yml）

### 6.3 配置分类

| 配置类型 | 说明 | 示例 |
| :--- | :--- | :--- |
| 服务配置 | 端口、服务名 | `server.port`, `spring.application.name` |
| Nacos配置 | 服务发现、配置中心 | `spring.cloud.nacos.*` |
| 数据源配置 | 数据库连接 | `spring.datasource.*` |
| 业务配置 | 自定义业务参数 | `epost.express.*` |

### 6.4 快递服务商配置规范

快递服务商支持通过配置文件进行启用/停用控制：

```yaml
express:
  carriers:
    ems_internal:
      name: EMS公司内下单
      enabled: true
      apiUrl: https://api.ems.com
      appKey: ${EMS_APP_KEY}
      appSecret: ${EMS_APP_SECRET}
      timeout: 30000
      maxRetry: 3
```

**配置说明：**

| 配置项 | 类型 | 说明 |
| :--- | :--- | :--- |
| `enabled` | Boolean | 是否启用该快递服务商，默认为true |
| `name` | String | 快递公司名称 |
| `apiUrl` | String | API接口地址 |
| `appKey` | String | API密钥（使用环境变量注入） |
| `appSecret` | String | API密钥秘钥（使用环境变量注入） |
| `timeout` | Integer | 请求超时时间（毫秒） |
| `maxRetry` | Integer | 最大重试次数 |

**启用/停用机制：**
- 当 `enabled` 设置为 `false` 时，该快递服务商将在系统启动时被过滤，不纳入可用策略列表
- 被禁用的快递服务商调用时将返回"不支持的快递公司编码"错误
- 默认情况下，如果未配置 `enabled` 字段，则视为启用

## 7. API规范

### 7.1 RESTful 设计原则

- **资源命名**: 使用名词复数
- **HTTP方法**:
  - `GET`: 查询资源
  - `POST`: 创建资源
  - `PUT`: 更新资源（完整替换）
  - `PATCH`: 更新资源（部分更新）
  - `DELETE`: 删除资源

### 7.2 响应格式

统一响应格式：

```json
{
  "code": 200,
  "message": "success",
  "data": {},
  "timestamp": 1779874767000
}
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `code` | Integer | 状态码（200成功，其他为错误码） |
| `message` | String | 响应消息 |
| `data` | Object | 响应数据 |
| `timestamp` | Long | 时间戳 |

### 7.3 错误码规范

| 错误码 | 含义 | 使用场景 |
| :--- | :--- | :--- |
| 200 | 成功 | 请求成功 |
| 400 | 参数错误 | 请求参数校验失败 |
| 401 | 未授权 | 未登录或Token失效 |
| 403 | 无权限 | 权限不足 |
| 404 | 资源不存在 | 请求的资源不存在 |
| 500 | 服务器错误 | 系统内部错误 |
| 503 | 服务不可用 | 依赖服务不可用 |

### 7.4 接口版本控制

- 使用URL路径方式：`/api/v1/express/orders`
- 版本号使用 `v1`, `v2` 格式
- 旧版本接口保留一段时间后逐步废弃

## 8. 安全规范

### 8.1 输入验证

- 使用 `@Valid` 注解进行参数校验
- 对用户输入进行严格的类型和长度校验
- 防止SQL注入、XSS攻击
- 使用参数化查询（MyBatis自动处理）

### 8.2 敏感信息保护

- 禁止日志打印密码、Token、手机号、身份证等敏感信息
- 数据库存储密码需加密
- API响应中脱敏处理敏感字段

### 8.3 接口安全

- 所有接口需进行权限校验
- 使用JWT Token进行身份认证
- 配置接口访问频率限制
- HTTPS协议传输

### 8.4 依赖安全

- 定期扫描第三方依赖漏洞
- 使用 Maven 依赖检查插件
- 及时更新存在安全漏洞的依赖

## 9. 测试规范

### 9.1 测试分类

| 测试类型 | 说明 | 覆盖率要求 |
| :--- | :--- | :--- |
| 单元测试 | 测试单个方法/类 | 核心业务代码 ≥ 80% |
| 集成测试 | 测试模块间交互 | 关键流程覆盖 |
| API测试 | 测试REST接口 | 所有接口覆盖 |

### 9.2 测试命名规范

- 测试类: `{ClassName}Test`
- 测试方法: `test{MethodName}_{Scenario}`

### 9.3 测试数据管理

- 使用测试专用数据库
- 测试数据独立，互不影响
- 测试完成后清理测试数据

## 10. Git规范

### 10.1 分支管理

- **main**: 主分支，稳定版本
- **develop**: 开发分支，功能集成
- **feature/{feature-name}**: 功能开发分支
- **bugfix/{bug-id}**: Bug修复分支
- **hotfix/{issue-id}**: 紧急修复分支

### 10.2 提交规范

提交信息格式：

```
<type>(<scope>): <subject>

<body>

<footer>
```

| 类型 | 说明 |
| :--- | :--- |
| `feat` | 新功能 |
| `fix` | Bug修复 |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响逻辑） |
| `refactor` | 代码重构 |
| `test` | 测试相关 |
| `chore` | 构建/工具更新 |

示例：
```
feat(express): 新增EMS下单接口

- 实现EMS快递下单逻辑
- 添加参数校验
- 集成策略模式
```

### 10.3 代码审查

- 合并到 develop 分支前必须经过代码审查
- 至少需要1位评审人批准
- 审查内容包括：代码质量、安全性、合规性
